# UV-K5 V1 (KD8CEC) — SARSAT screen integration

Base: **KD8CEC `uvk5cec-0.3q`** source (egzumer lineage, DP32G030 / BK4819).
Reproduce with `./build.sh /path/to/uvk5cec-0.3q` → `bin/uvk5-cec-0.3q-sarsat.packed.bin`.

Toolchain: `arm-none-eabi-gcc` 13.2 (native), `make`, `python3` + `crcmod`
(`pip install --user --break-system-packages crcmod`). No Docker, no J-Link — the
Makefile's `openocd` steps live only in the `debug` / `flash` targets.

FLASH: **56 772 B text + 16 B data** of 60 KiB (headroom ~4.6 KiB) with
`MAIN_SCREEN=moto`. The APRS RX view renders a structured Kenwood-style decode
with a 16x16 symbol icon; `ENABLE_AUDIO_BAR` is turned off in `build.sh` (the TX
mic-level bar overlay is unused here) to keep the margin.

## Main VFO screen — `MAIN_SCREEN = stock | moto | id91`

`patch/ui_main.c.diff` gates an alternate `UI_DisplayMain()` (+ `DisplayRSSIBar()`
body) behind the `MAIN_SCREEN` make variable. `build.sh` picks `moto`.

- **`stock`** — the original egzumer/KD8CEC dual-VFO screen, completely untouched.
  Text **56 892 B** (heaviest — the original function is large).
- **`moto`** — MOTOTRBO DP/GP idiom: inverted round-cornered header (row 0);
  **frequency in a 24 px condensed-bold font** (`MOTO_DIG`, ~450 B, generated by
  `tools/gen_bigdigits.py`) on rows 1-3; centred detail line (row 4); an
  **antenna + 5 rising bars** S-meter with `-84 dBm S6` (row 5, `DisplayRSSIBar`
  alt body); the other VFO on row 6. Text **56 712 B** (−180 vs stock).
- **`id91`** — same layout, but reuses primitives already in the firmware:
  `UI_DisplayFrequency` / `gFontBigDigits` (16 px, rows 1-2) for the frequency
  and the **stock horizontal segmented S-meter** (`DrawLevelBar`) on row 4.
  Text **56 492 B** (**−400 vs stock, −220 vs moto**).

Shared helpers `MainHeader` / `MainDetail` / `MainIdleVfo`. Both redesigns handle
frequency / MR-channel (all `MDF_*`) / frequency-input / `VfoState` strings /
scan-ranges; all writes stay in `gFrameBuffer[0..6]`; no bottom soft-key bar (the
UV-K5 has none under the LCD). All three compile `-Wextra` clean. Not yet tested
on hardware; `gDTMF_InputMode` (manual DTMF entry) is not drawn in moto/id91.

## What it does

The RP2040 C-Board decodes COSPAS-SARSAT 406 MHz 1st-generation beacons from the
radio's FM-RAW audio and pushes formatted text lines to the radio over the
standard Quansheng UART frame. This firmware adds a screen to show them.

- **Auto-open:** on the first `0x06C1` (SARSAT_TEXT) the radio switches to the
  SARSAT screen.
- **Manual open:** **F + 8** (replaces the F+8 "frequency reverse" shortcut when
  `ENABLE_SARSAT=1`).

Set the selected VFO to a 406 MHz beacon frequency (406.025 / 406.028 /
406.037 MHz) before opening the screen — SARSAT mode just receives *there*,
it does not scan.
- **Scroll:** **UP / DOWN** (the decode is word-wrapped to ~12-14 short lines;
  6 rows + a header row are visible — the LCD content area is 7 rows).
  Header shows `SARSAT n-m/total ^v`.
- **`5`:** toggle between the beacon text and the **audio level** screen
  (rms / peak / dc / clip / adc range + bar + a verdict line). **UP/DOWN on the
  level screen tune the BK4819 AF gain** feeding the C-Board — put the volume
  pot to max and adjust against the rms bar; saved to EEPROM. The RP2040 sends
  `0x06C3 SARSAT_LEVEL`. **On this screen the C-Board switches to short
  ~125 ms capture windows so the bar refreshes at ~7 Hz** (vs ~1 Hz on the
  decode view) — the radio flags the level view in its HELLO reply (`screen=2`)
  and re-sends it immediately on the `5` toggle, so it kicks in at once.
  Decoding is paused while you're on this screen. **Tune the hiss to the middle of the bar
  (`OK reglage correct`, dc mid-scale, clip 0 %) — do NOT push it hot to chase
  the beacon.** The RP2040 detects a burst *relative* to the tracked hiss floor
  (`CFG_BURST_QUIET_PCT`, a captured 406 MHz burst reads 6–12 dB below the
  hiss), so it decodes at any clean gain. The `fort: APRS sature` verdict is a
  caution that the gain is high enough that a strong 2 m APRS packet would clip
  the shared audio tap — back it off. The SARSAT screen always (re)opens on the
  decode view, never the level view.
- **Close:** **EXIT**.

## APRS tracker (`ENABLE_APRS`)

**F + 5** opens the APRS config / status screen (the freed spectrum slot):

UP/DOWN move the selection through the fields (Call, SSID, Path, Icon,
Interval, Popup, AF gain, Squelch, Light, Lat, Lon); row 0 is the header, rows 1-6 are a scrolling window over
the fields (`^`/`v` in the header when there is more above/below). MENU enters
edit on the selected row, MENU again saves, EXIT cancels (reloads from EEPROM).
The header shows the context-sensitive key help.

| field | edit |
|-------|------|
| Call | UP/DOWN change the char, `*` moves the cursor (6 chars) |
| SSID | UP/DOWN 0..15 |
| Path | UP/DOWN none / WIDE1-1 / WIDE2-1 / WIDE1-1,WIDE2-1 |
| Icon | UP/DOWN car / house / truck / runner / bike / yacht / plane / wx / dot |
| Interval | UP/DOWN OFF / 30 / 60 / 120 / 300 / 600 / 900 / 1800 s (auto-beacon) |
| Popup | UP/DOWN OFF / 5 / 10 / 20 s — auto RX-view popup on a decoded packet, auto-closes after N s (a key cancels the timer) |
| AF gain | UP/DOWN auto / 1..78 — a combined slider over the BK4819 REG_48 AF Rx Gain-2 + DAC gain (~-52 dB at 1, stock at 78); it sweeps Gain-2 63->8 first (linear region), then the DAC gain 15->0. Both are re-applied on every SARSAT / APRS screen open and ~2x/s from the tick (`patch/radio.c.diff` stops `RADIO_SetModulation()` forcing the DAC gain to max, which was the "louder after reopen" bug) feeding the C-Board tap. Set the volume pot to max and tune this; also adjustable on the SARSAT level screen against the rms bar. `auto` = stock. Persists via `gEeprom.DAC_GAIN` / `.VOLUME_GAIN` so `RADIO_SetupRegisters` keeps it — no radio.c patch. |
| Squelch | UP/DOWN toggle **`Squelch fast`** (default) / **`Squelch stock`**. `fast` drops the BK4819 squelch **open delay** (REG_4E bits 13:11) from 5 to 0 **only while the RX VFO is 144–148 MHz**, so the receiver un-mutes within a couple of ms and the first AX.25 flags of a packet aren't lost. Re-asserted every 10 ms tick (a VFO re-config rewrites REG_4E). Off-band = untouched. For truly zero loss, set the radio's own `SQL` menu to 0 (monitor). |
| Light | UP/DOWN toggle **`Light on RX`** (stock — backlight on any squelch open) / **`Light on frame`**. With `Light on frame`, while the RX VFO is 144–148 MHz the RX-squelch backlight is suppressed and the screen lights **only when the C-Board decodes an APRS packet** (`APRS_QuietBacklight()` gates the `BACKLIGHT_ON_TR_RX` call in `APP_StartListening`; `aprs_rx_arrived()` calls `BACKLIGHT_TurnOn()`). Off-band the radio behaves normally. |
| Lat / Lon | **type the digits** (2+5 for lat, 3+5 for lon, decimal auto-placed), `*` toggles N/S resp. E/W; or UP/DOWN for ±0.001° steps when nothing is typed. No GPS yet. |

**5** = beacon now. Config is saved to EEPROM **`0x1D00`** (40 B) — *not*
`0x1D50` (`CEC_EEPROM_START1`): `SETTINGS_SaveSettings()` rewrites the first
8 bytes there with the KD8CEC CW / live-seek settings on every menu change,
which was wiping the APRS magic + callsign ("APRS config reverts to default").
`0x1D00` (`CEC_EEPROM_START2`) is in the DTMF-contacts region but past the 16
real contacts, protected from factory reset, and unused by 0.3q.
`APRS_Init()` is not on the boot path; it runs lazily (EEPROM read) the first
time the beacon tick, the screen, or an RX frame touches the config.

The screen keeps the backlight on and refreshes the auto-keypad-lock timer on
every key while it runs, and on exit reselects the VFOs
(`RADIO_SelectVfos()` + `RADIO_SetupRegisters(true)`) and refreshes both timers
— the main loop is blocked while the screen is up, so its dual-watch / VFO
bookkeeping and its backlight + key-lock countdowns are all stale on return
(that was the "VFO B disappears / keypad locks after exit" bug).

**TX path:** `app/aprs.c` builds the AX.25 UI frame (`app/ax25.c`: FCS-16/X.25,
bit-stuffing, NRZI — host-tested by `rp2040/test/host/test_ax25`), then keys the
PA exactly like `FUNCTION_Transmit()` (`BK4819_DisableDTMF()` +
`RADIO_SetTxParameters()` + red LED) and generates Bell-202 AFSK the same way
the firmware does its roger beep: `BK4819_EnterTxMute()` → `REG_70` tone1 (gain
`AFSK_TONE_GAIN`, default 64 — **lower it if the packet is over-deviated**) →
`BK4819_EnableTXLink()` → settle → set `REG_71` and `BK4819_ExitTxMute()`, then
run the bit stream: `REG_71` is rewritten **only on an actual tone change**
(so NRZI runs stay phase-continuous) and each bit cell is clocked off a
free-running **SysTick deadline** (`AFSK_TICKS_PER_BIT = 48 MHz / 1200`) that
absorbs the ~40 µs `BK4819_WriteRegister` cost and self-corrects for IRQ
jitter — average stays exactly 1200 baud. 40 opening flags, 3 closing.
~0.6 s on air. **No mic/PTT wiring** — the radio does it all, KD8CEC-style.
**Validated on hardware**: transmitted packets decode cleanly on an external
APRS TNC.

> Two first-cut bugs, both fixed:
> - **`REG_30` by hand** without `ENABLE_PA_GAIN` / `ENABLE_PLL_VCO` collapsed
>   the PA while the PA-enable GPIO and red LED stayed on ("keys up, nothing
>   radiates"). `BK4819_EnableTXLink()` sets `REG_30` correctly for TX DSP.
> - **`WriteRegister` every bit + `SYSTICK_DelayUs(820)`** made each cell
>   ~860 µs (3 % slow) and jittery — no TNC could lock. The deadline clock
>   plus change-only `REG_71` writes fixed it.

> Set the APRS VFO to a legal **144.800 MHz simplex** channel before beaconing —
> `APRS_Beacon()` keys TX with only a "not already transmitting / callsign set"
> guard, it does not re-check band/lockout.

**RX:** the RP2040 C-Board demodulates 144.8 MHz APRS (Bell-202 AFSK 1200 +
AX.25, `rp2040/src/aprs_rx.c` -- 3 parallel biased slicers + a single-bit-flip
FCS repair for Dire-Wolf-style error recovery, since AX.25 carries no FEC),
**parses the info field** (`rp2040/src/aprs_parse.c` -- uncompressed / compressed
/ MIC-E / object / item / status / message) and pushes a structured `0x06D3`
decode: symbol, lat/lon, course/speed/altitude, and range + bearing to the
operator (computed on the RP2040 from the position the radio puts in its HELLO
reply). The RX view draws it Kenwood-style -- a **16x16 symbol icon** (aprs.fi-style set
incl. `/r` repeater tower), object name or source call + packet age, lat/lon,
range/bearing, course/speed/altitude, then the wrapped comment/status/message
text. A packet whose info field is not understood falls back to `0x06D2` raw
text (source call on line 0, wrapped info below). The view opens straight to the
RX display whenever a packet -- structured **or** raw -- has been decoded
(`APRS_HasRx()`); earlier it fell back to the config menu after a structured
decode because the raw-text buffer was empty.
On a decode the RX view **pops up automatically** (per the Popup
setting: OFF / 5 / 10 / 20 s; a 5 s cooldown only if you pressed **EXIT** to
dismiss it — a plain timed close lets the next packet pop right away). F + 5 also opens
it. The **auto-popup hides the `APRS RX … *:cfg` title line** and shifts the
packet up one row for a cleaner glance; the title is shown only when you open
the view yourself (F + 5). In the RX view **`*`** → config, **EXIT** → close (back to VFO). RX stays
live under the popup so the C-Board keeps decoding — a **packet arriving under
the popup is shown too and re-arms the auto-close timer**. The screen runs a
mini squelch (polls the BK4819 SQUELCH interrupt, toggles the speaker path +
RX LED) so the between-packets channel noise isn't heard while the main loop
is blocked. The
C-Board auto-switches to APRS decoding whenever the radio's RX VFO is
144–148 MHz (from the HELLO reply).

*Nothing on the RX view?* Check the RP2040 USB console: a `[aprs] mode APRS`
line must appear (the radio's HELLO must report 144–148 MHz), then
`[aprs] #N SRC>...` on each decode. No decode = level / tuning issue on the
C-Board tap, same as SARSAT. The RP2040 has an **IF limiter** so a *strong*
signal no longer distorts the demod — but watch the `clip=NN.N%` field in the
`[aprs]` line: above ~2 % the ADC is railing and you should lower the AF gain
(`Squelch fast` + AF-gain slider, or the radio's volume).

*TX LED blinks during RX?* That is the **auto-beacon** — set **Interval = OFF**
for RX-only testing. `APRS_Beacon()` / `APRS_TimeSlice()` now also hold off
while the channel is busy (`FUNCTION_RECEIVE` / `FUNCTION_MONITOR`), so a beacon
no longer keys up on top of an incoming packet.

### Flash budget

`build.sh` disables `ENABLE_SPECTRUM`, `ENABLE_FMRADIO` (broadcast), `ENABLE_VOX`,
`ENABLE_FLASHLIGHT` and `ENABLE_AUDIO_BAR`. SARSAT + level screen + APRS TX +
config screen + structured RX view with 16x16 icons + `MAIN_SCREEN=moto`:
**56 788 B of 61 440, ~4.5 KB free** (`id91` −220 B, `stock` +180 B).
- The RP2040 sends `CLEAR` + one `0x06C1` per line ~8 ms apart; `APP_RunSarsat()`
  drains with `while (UART_IsCommandAvailable()) UART_HandleCommand();` so no
  line is lost to the 256-byte UART ring.
- **Entry is guarded:** `APP_RunSarsat()` returns immediately (leaving
  `gSarsatShowRequest` pending for the next 10 ms tick) unless the radio is idle
  on `DISPLAY_MAIN`. Opening this blocking screen over a menu left the display
  and VFO state wrecked — garbage screen, stuck in MR after a power cycle.
- **Exit is synchronous and complete.** The screen can be auto-opened from the
  10 ms tick, not only from a key, so it cannot lean on the key-handler tail to
  finish cleanup. On EXIT it: `FUNCTION_Select(FUNCTION_FOREGROUND)` (leave
  `FUNCTION_MONITOR`, else the next key just "stops monitoring" and seems dead),
  restores `gEeprom.RX_VFO`, **`RADIO_ConfigureChannel(0/1, VFO_CONFIGURE)`**
  (re-reads both VFOs from EEPROM and *validates* `gEeprom.ScreenChannel` — a
  stray value showed as **"M128, no name/freq" and stuck**, because the tick has
  no key-handler tail to run the reconfigure), `RADIO_SelectVfos()` +
  `RADIO_SetupRegisters(true)`, `BACKLIGHT_TurnOn()` + `gKeyLockCountdown = 30`,
  `GUI_SelectNextDisplay(DISPLAY_MAIN)` **now**, and clears `gSarsatShowRequest`.
- **Frequency:** the currently *selected* VFO (`gEeprom.TX_VFO`,
  `gTxVfo->pRX->Frequency`). On entry it forces `gRxVfo = gTxVfo` /
  `gEeprom.RX_VFO = gEeprom.TX_VFO` and re-tunes; on exit `RADIO_SelectVfos()`
  recomputes the real RX VFO (dual-watch / cross-band).
- **Squelch:** forced open. Entry calls `APP_StartListening(FUNCTION_MONITOR)`
  (→ `AUDIO_AudioPathOn()`, `gEnableSpeaker = true`, squelch disabled) so the
  C-Board tap always hears the RF. `gMonitor` is cleared on exit.
  *(A plain `FUNCTION_Select(FUNCTION_MONITOR)` only sets a flag and does not
  open the audio path — that was the first-cut bug.)*
- **Demodulation: `MODULATION_FM` (the FM discriminator)**, WIDE IF, plus
  REG_2B bits 10/9/8 to drop RX de-emphasis / HPF300 / LPF3k so the bi-phase-L
  transitions pass flat. Applied **after** `APP_StartListening` (which resets
  the modulation to the VFO's own).
  - **Not** `MODULATION_RAW` / `BK4819_AF_BASEBAND1`: that is an SSB-style raw
    output; it beats the strong 406 MHz beacon carrier against the tuned
    frequency into a **constant whistle**. The discriminator turns a small
    tuning error into a slow DC drift instead, which the RP2040 slicer removes.
  - If the flat-AF hiss is worse than the flatness helps, delete the REG_2B
    write in `app/sarsat.c` → plain wide FM.

  The same flat-discriminator profile is now also a **user-selectable
  modulation, `DSC`**, in the `Demodu` menu (`patch/radio.h.diff` adds
  `MODULATION_DISCRI`, `patch/radio.c.diff` sets/clears the REG_2B de-emphasis
  bits in `RADIO_SetModulation` — every other mode restores stock filtering).
  `Demodu → DSC` (+ `W/N → Wide`) gives the SARSAT profile on a normal channel,
  e.g. for feeding the C-Board on the 144.8 APRS channel. The SARSAT screen
  still forces its own FM+WIDE+REG2B regardless of the channel's `Demodu`.

UART: unchanged. The DualTachyon divisor `UART1->BAUD = Frequency / 39053`
already yields ≈ 38400 8N1, which is what the RP2040 side uses
(`CFG_RADIO_UART_BAUD 38400`).

## Serial commands handled (added to `UART_HandleCommand`)

| ID | payload | action | reply (`ID \| 0x8000`) |
|----|---------|--------|------------------------|
| `0x06C0` | — | clear the line buffer + reset scroll | `{status:u8}` |
| `0x06C1` | `line:u8, invert:u8, ascii[0..20]` | set one line; invert → bold; auto-open | `{status:u8}` (1 = bad line index) |
| `0x06C2` | (reserved, ignored) | — | `{status:u8}` |
| `0x06CF` | `proto_ver:u8` | keepalive | `{vfo:u8, modulation:u8, rx_freq:u32 LE 10 Hz, screen_open:u8, proto:u8}` |

**Phase 2 (radio → RP2040):** every `0x06Cx` gets a reply via `SendReply()`
(made non-static in `patch/app_uart.c.diff`). The `0x06CF` reply carries the
radio's live state so the RP2040 can log the link and warn if the radio is not
on FM / not near 406 MHz. `modulation` is reported as FM while the SARSAT screen
is open (it forces FM), otherwise the selected VFO's own modulation.

Full protocol: `../../docs/protocol.md`.

## The 18-glyph rule (why the display corrupted the EEPROM)

`UI_PrintStringSmall*` **does not clip**. At the `Start = 2` column these
screens use, the 6px glyph / 7px pitch font runs off the end of a
`gFrameBuffer[row]` (128 bytes) after **18 glyphs** — the extra bytes land in
the *next* row, and from the bottom row (6) they land in **`gEeprom`**, which
the linker puts 2 bytes past `gFrameBuffer`. That corrupted `ScreenChannel`
("stuck on M128"), `VFO_OPEN`, `KEY_LOCK`, `DUAL_WATCH`… and showed as garbage
at the start of the row below.

Every string sent to `UI_PrintStringSmall*` in `sarsat.c` / `aprs.c` is now
`<= 18` glyphs: `SARSAT_LINE_CHARS` 21 → 18, the level-screen bar 21 → 16, all
headers / verdict strings trimmed, the APRS RX text 18 and formatted compact
(source callsign + wrapped info, no dst / digi path). The RP2040 word-wraps the
SARSAT decode and the APRS packet to 18 too.

## Known-bad early builds — EEPROM recovery

`gEeprom` is linked **2 bytes past `gFrameBuffer`** (`gFrameBuffer[7][128]`
followed immediately by `gEeprom[256]`). An early build of this fork wrote
text to LCD "line 7" in the SARSAT screen (`SARSAT_VIS_ROWS` was 7, and the
level screen's verdict row was 7) — the on-screen area is only 7 rows
(`gFrameBuffer[0..6]`), so those writes landed **inside `gEeprom`**, corrupting
`ScreenChannel` / `VFO_OPEN` / `KEY_LOCK` / `DUAL_WATCH` … Symptoms after a
decode + a power cycle: garbage screen, **stuck in MR with F+3 (VFO/MR) dead**,
keypad locked, APRS/other settings reset.

Current builds write nothing past row 6, so they cause no new corruption — but
**reflashing does not repair the EEPROM**. Recovery:

1. Flash a current build.
2. Keypad locked? Long-press **`#`** (the F key) to unlock.
3. **F + 3** → back to VFO mode. (`patch/settings.c.diff` also forces
   `VFO_OPEN = true` on every boot, since 0.3q has no menu for it — that alone
   re-enables F+3.)
4. Fix squelch / dual-watch / cross-band from the menu if they look wrong.
5. If still inconsistent: menu **factory reset**, then reprogram channels.

`APP_RunSarsat()` is a blocking full-screen loop modelled on `APP_RunSpectrum()`
(the K5 firmware runs no hardware watchdog, so blocking is safe). It pumps
`UART_IsCommandAvailable()/UART_HandleCommand()` itself so text keeps updating
live while the screen is open.

## Not done / notes

- 2nd-generation (SGB) beacons: out of scope (RP2040 decodes 1G only).
- `0x06C2 SARSAT_BEACON` (binary struct) is accepted but ignored; the RP2040
  currently drives everything through `0x06C1` text.
- No new menu entry / EEPROM setting — the feature is compile-time (`ENABLE_SARSAT`)
  and needs no configuration.
- Not tested on hardware yet.
